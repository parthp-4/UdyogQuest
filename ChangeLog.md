## 2026-08-18 - Fix: production client crash on assistant answers ("missingInformation.map is not a function")

- Prompt: user reported a full-page "Application error: a client-side exception has occurred" on `udyog-quest.vercel.app` when using the AI assistant, with browser console error `TypeError: u.missingInformation.map is not a function`.
- Root cause: `lib/ai/gemini.ts` `askGeminiFromSources()` did `JSON.parse(text) as AssistantAnswer` on Gemini's raw JSON output with no runtime validation. The system prompt named the `missingInformation` field but never stated it must be a JSON *array* of strings. Gemini (non-deterministically) sometimes returns it as a plain string instead -- this was actually observed and printed during the prior session's own live verification (`"missingInformation":"Detailed provisions, specific clauses..."`) but wasn't recognized as a type-contract violation at the time. That malformed shape flowed straight through to `components/forms/assistant-panel.tsx`, which called `answer.missingInformation.map(...)` unconditionally -- a string has no `.map`, so the render threw and Next.js's client error boundary took over the whole page.
- Changed:
  - `lib/ai/gemini.ts`: added `normalizeAssistantAnswer()`, applied to every parsed Gemini response before it's returned. Coerces `missingInformation` to always be `string[]` (wrapping a lone string, defaulting to `[]` for anything else), `citations` to always be an array, `answer`/`suggestedNextAction` to always be strings -- regardless of what Gemini's JSON actually contained.
  - `lib/ai/system-prompt.ts`: rule 8 now explicitly states the required type of each JSON field ("missingInformation (array of strings -- use an empty array if nothing is missing, never a single string)") -- reduces how often the model emits the wrong shape, but is not relied on alone.
  - `components/forms/assistant-panel.tsx`: `ask()` now normalizes the raw fetch response into the exact `AssistantResponse` shape (guarding `Array.isArray` on `citations`/`missingInformation`, `typeof === "string"` on `answer`/`suggestedNextAction`) before calling `setAnswer`, as a second, independent layer -- the client should not fully trust the API response's shape either, since it crosses a network boundary.
- Verification:
  - `npm run typecheck`: clean (after a first pass that failed -- `Partial<AssistantAnswer>` typing made the string-fallback branch unreachable/`never`-typed; switched to reading the raw parsed JSON as `Record<string, unknown>` instead, which is what runtime validation of an actually-untrusted value requires).
  - `npm test` (vitest): 56/56 pass (unaffected -- no existing test covered this path).
  - `npm run build`: succeeds.
  - Ran the real dev server against the real `.env.local` (LIVE mode, real `GEMINI_API_KEY`) and called `POST /api/assistant` with the same DGFT question multiple times in a row, saving and inspecting the raw HTTP response bytes each time: every response was valid JSON with `missingInformation` as a JSON array (including the two transient real `503 UNAVAILABLE` Gemini-overload responses encountered mid-testing, and three genuine successful cited answers) -- the exact failure mode is confirmed fixed, not just typed away.
- Notes: this shipped in the same release as the Vercel-readiness audit's Gemini model-name fix (`gemini-2.5-flash` -> `gemini-3.6-flash`), which is what made the assistant's success path reachable at all in production -- this crash was the very next bug behind it, only visible once real answers started coming back. Document extraction (`lib/documents/extract.ts`) uses a different, structured (non-freeform-array) response shape and was not affected, but was not independently re-audited for the same class of issue in this pass.
